Abstract

Centralized cloud password vaults introduce single points of catastrophic failure: ciphertext databases stored online invite offline brute-force attacks upon server breach, while cloud recovery backdoors create social engineering vectors. FrankPass presents an open, client-side, deterministic password derivation architecture that eliminates digital password storage entirely.

FrankPass formalizes the Canonical Protocol Parameter Tuple, designated as Master Manikant Yadav's Constant (ℳℳ𝒴constant): an immutable 7-parameter architectural tuple combining 1,000,000 rounds of PBKDF2 with HMAC-SHA512 continuous stream expansion, comprehensive natural language whitespace/casing normalization, Unicode NFC parity, and a zero-modulo-bias Golden Base-32 character mapping pool (25 = 32).

This specification documents the mathematical properties, entropy formulations (80 to 100 bits of true search entropy), threat modeling, and lifetime determinism invariants that allow users to generate identical, unguessable credentials across decades without transmitting a single byte over the network.

1. Background & Problem Statement

Traditional password management systems rely on encrypted server vaults: Ci = EK(Pi), where ciphertexts Ci are stored on cloud infrastructure. This architecture suffers from three structural vulnerabilities:

  1. Server-Side Exfiltration Risk: Storing encrypted vaults on remote servers creates high-value honeypots. A server breach permits adversaries to download ciphertext backups and run multi-GPU offline brute-force attacks indefinitely.
  2. Credential Recovery Backdoors: Server-side account recovery interfaces (SMS OTP, email reset links) bypass master encryption keys, causing the majority of SIM swap and account takeover attacks.
  3. Vendor Lock-in & Server Availability: If the vault provider experiences service outages, changes pricing models, or terminates operations, users risk losing access to their credentials.

FrankPass solves these structural flaws by replacing vault storage with pure deterministic client-side mathematical key derivation.

2. Stateless Architecture & The Determinism Invariant

In a stateless password architecture, passwords are never stored in databases, memory cookies, or cloud blobs. Instead, passwords are generated on demand as a pure deterministic function of four user inputs and one permanent architectural tuple:

Password = f(MasterSecret, Platform, Username, Version, ℳℳ𝒴constant)

The Necessity of Immutability (Why ℳℳ𝒴constant is Frozen)

Honest Architectural Clarification: Master Manikant Yadav's Constant (ℳℳ𝒴constant) is not a physical constant of nature (such as Planck's constant or the gravitational constant). Rather, it is a formally locked architectural and cryptographic invariant established by Master Manikant Yadav.

In a stateless key derivation system, if any internal parameter (such as iteration count, hash algorithm, context vector structure, or character mapping table) were to change in future software releases, the deterministic output would alter completely. Users would be forced to reset all their account passwords across the internet. Freezing this parameter tuple permanently guarantees that a credential derived today will generate byte-for-byte identically 10, 20, or 50 years from now on any standards-compliant computing device.

5. Golden Base-32 Pool & Mathematical Proof of Zero Modulo Bias

Traditional random generators that map byte arrays (0 to 255) to arbitrary character pool sizes (e.g. 55, 62, or 94 characters) suffer from Modulo Bias unless unaligned bytes are systematically rejected and discarded.

FrankPass solves this problem mathematically by utilizing an exact Golden Base-32 Character Pool (𝒞, where |𝒞| = 32 = 25):

Mathematical Proof of Zero Modulo Bias & Policy Mapping:

Let B ∈ {0, 1, ..., 255} be a uniformly distributed pseudorandom byte generated by HMAC-SHA512. The maximum aligned boundary validMax is calculated as:

validMax = 256 - (256 mod 32) = 256 - 0 = 256

Because 256 is an exact integer multiple of 32 (28 / 25 = 23 = 8 exact full cycles):

∀ c ∈ 𝒞,   P(byteToChar(B) = c) = 8 / 256 = 1 / 32 = 0.03125 (3.125%)

Every character in the 32-glyph alphabet has an identical selection probability of exactly 1/32 (3.125%). Modulo bias rejection loss is mathematically 0.000%.

Deterministic Character Policy Enforcement:

To satisfy external security policies in the 'standard' profile (mandatory presence of uppercase, lowercase, digit, and symbol), frankpass-core.js executes a deterministic 2-stage mapping:

  1. Primary Stream Mapping: The first L pseudorandom bytes are mapped directly via Base-32 modulo conversion.
  2. Deterministic Injection: If any required category is absent from the initial L characters, a replacement character from the missing category is deterministically injected at position byteStream[revIdx] % targetLength using the tail of the 128-byte pseudorandom buffer.

By the principle of inclusion-exclusion, the constrained search space of passwords containing at least one character from each required subset for L = 16 is:

|Ωvalid| = 3216 - ∑ (Excluded Combinations) ≈ 1.199 × 1024  &implies;  Heffective ≈ 79.95 bits

Policy enforcement preserves maximum search space complexity, remaining practically indistinguishable from unconstrained 80.00-bit entropy.

Crucial Distinction: Master Secret Entropy vs. Output Search Space

A fundamental principle of applied cryptography is that a Key Derivation Function (KDF) cannot synthesize entropy from nothing. The real-world work factor for an adversary targeting a specific user is strictly bounded by:

Effective Security = min(Hpassphrase, KDF Bit Security)

While an output length of 16 characters (80 bits search space) or 20 characters (100 bits search space) prevents accidental collisions and satisfies strict target system constraints, an attacker who extracts a derived password from a third-party breach will brute-force the input passphrase space, not the output space. 1,000,000 iterations of PBKDF2-HMAC-SHA512 impose massive computational penalties on GPU/ASIC crackers, but baseline security remains bounded by the entropy of the user's secret.

Architectural Recommendation: Users should generate passphrases using independent random word selection (Diceware / EFF wordlist style, yielding ~65 to 80 bits of true entropy for 5-6 words) or memorable personalized phrases exceeding 7 to 9 words.

7. Usable Security & The Science of Input Normalization

In deterministic key derivation systems, human typing variability is the primary operational failure point. When entering a master secret on mobile devices, modern virtual keyboards introduce automatic transformations:

  • Automatic capitalization of the first letter (e.g. MySecret vs mysecret).
  • Automatic insertion of smart punctuation or directional quotes.
  • Trailing whitespace added during auto-complete suggestions.

In un-normalized systems, a single accidental space alters the entire derived password, causing authentication failures. FrankPass incorporates MMY Comprehensive Input Normalization (𝒩norm) and Unicode NFC Composition (𝒫NFC) before derivation:

// Exact Canonical Normalization Implementation:
const normalizedSecret = (secretKey || '')
    .toLowerCase()
    .replace(/\s+/g, '')
    .replace(/[^a-z0-9]/g, '');

This guarantees that variations such as "Master Secret 2026! ", "mastersecret2026", and "master secret 2026" always map to the exact same canonical byte array, eliminating cross-device human error.

Cryptographic Trade-Off of Normalization

Honest Architectural Disclosure: Normalization restricts the effective character pool of the Master Secret to 36 alphanumeric characters ([a-z0-9], ~5.17 bits per character). Any complexity added through uppercase letters, punctuation, or spaces is discarded during canonicalization.

Consequently, users should build security through passphrase length and word count rather than relying on complex single-character substitutions (e.g. using P@$$w0rd! is ineffective; using mango river copper guitar 2026 is highly effective).

8. Threat Model & Endpoint Defense Matrix

📐 Formal Cryptographic Assumptions

  • Assumption A1 (PRF Security): HMAC-SHA512 operates as a cryptographically secure Pseudorandom Function (PRF) with no known practical shortcut attacks.
  • Assumption A2 (Adversary Model): The adversary is offline and conducting an inversion / pre-image search against the deterministic derivation function from a leaked output password.
  • Assumption A3 (Runtime Integrity & Timing Resistance): Major browser engines implement W3C WebCrypto API primitives in native compiled C++ (e.g., BoringSSL, NSS); FrankPass relies on the host cryptographic libraries for standard constant-time execution and timing-attack resistance.

1. Server Compromise & Zero-Storage Immunity:

Because FrankPass servers store zero credentials, zero master keys, and zero ciphertext blobs (0 bytes stored), a total compromise of the hosting infrastructure, edge CDNs, or DNS routers eliminates server-side credential data storage, neutralizing database breach attack vectors.

2. Cryptographic Domain Separation & Threat Boundary:

By injecting the normalized domain slug into length-prefixed netstrings and salting the HMAC-SHA512 PRF, outputs across distinct platforms (D1 ≠ D2) are computationally independent. This eliminates cross-service password reuse and rainbow table attacks: a breach of Service A provides zero mathematical leverage to derive the password for Service B.

Cryptographic Boundary: Domain separation prevents credential cross-contamination, but cannot protect against full master secret compromise. If an adversary successfully brute-forces the user's Master Secret Key, passwords across all associated platforms can be computed. Security is fundamentally anchored in the Master Secret's entropy.

3. 100% Offline Architecture & Zero Network Attack Surface:

FrankPass web applications (PWA), desktop apps, mobile apps, and extensions are intentionally architected with zero runtime outbound network requests for credential generation. By eliminating server-side credential transmission endpoints, the threat of server-side data exfiltration and database breaches is eliminated by architectural design.

Once cached by the Service Worker or installed as a standalone application, FrankPass operates indefinitely on air-gapped, offline systems with 100% mathematical reproducibility.
