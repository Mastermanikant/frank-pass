Abstract

Centralized cloud password vaults introduce single points of catastrophic failure: ciphertext databases stored online invite offline brute-force attacks upon server breach, while cloud recovery backdoors create social engineering vectors. FrankPass presents an open, client-side, deterministic password derivation architecture that eliminates digital password storage entirely.

FrankPass formalizes Master Manikant Yadav's Constant (ℳℳ𝒴constant): a 7-parameter immutable architectural tuple combining 1,000,000 rounds of PBKDF2 with HMAC-SHA512 continuous stream expansion, aggressive natural language whitespace/casing normalization, Unicode NFC parity, and a zero-modulo-bias Golden Base-32 character mapping pool ($2^5 = 32$).

This specification documents the mathematical properties, entropy formulations ($80.000$ to $100.000$ bits of true search entropy), threat modeling, and lifetime determinism invariants that allow users to generate identical, unguessable credentials across decades without transmitting a single byte over the network.

1. Background & Problem Statement

Traditional password management systems rely on encrypted server vaults: $C_i = E_K(P_i)$, where ciphertexts $C_i$ are stored on cloud infrastructure. This architecture suffers from three structural vulnerabilities:

  1. Server-Side Exfiltration Risk: Storing encrypted vaults on remote servers creates high-value honeypots. A server breach permits adversaries to download ciphertext backups and run multi-GPU offline brute-force attacks indefinitely.
  2. Credential Recovery Backdoors: Server-side account recovery interfaces (SMS OTP, email reset links) bypass master encryption keys, causing the majority of SIM swap and account takeover attacks.
  3. Vendor Lock-in & Server Availability: If the vault provider experiences service outages, changes pricing models, or terminates operations, users risk losing access to their credentials.

FrankPass solves these structural flaws by replacing vault storage with pure deterministic client-side mathematical key derivation.

2. Stateless Architecture & The Determinism Invariant

In a stateless password architecture, passwords are never stored in databases, memory cookies, or cloud blobs. Instead, passwords are generated on demand as a pure deterministic function of four user inputs and one permanent architectural tuple:

Password = f(MasterSecret, Platform, Username, Version, ℳℳ𝒴constant)

The Necessity of Immutability (Why ℳℳ𝒴constant is Frozen)

Honest Architectural Clarification: Master Manikant Yadav's Constant (ℳℳ𝒴constant) is not a physical constant of nature (such as Planck's constant $h$ or the gravitational constant $G$). Rather, it is a formally locked architectural and cryptographic invariant established by Master Manikant Yadav.

In a stateless key derivation system, if any internal parameter (such as iteration count, hash algorithm, context vector structure, or character mapping table) were to change in future software releases, the deterministic output would alter completely. Users would be forced to reset all their account passwords across the internet. Freezing this parameter tuple permanently guarantees that a credential derived today will generate byte-for-byte identically 10, 20, or 50 years from now on any standards-compliant computing device.

5. Golden Base-32 Pool & Mathematical Proof of Zero Modulo Bias

Traditional random generators that map byte arrays ($0$ to $255$) to arbitrary character pool sizes (e.g. 55, 62, or 94 characters) suffer from Modulo Bias unless unaligned bytes are systematically rejected and discarded.

FrankPass solves this problem mathematically by utilizing an exact Golden Base-32 Character Pool ($\mathcal{C}$, where $|\mathcal{C}| = 32 = 2^5$):

  • Uppercase Alphabet (10 chars): ADEFHLMNRT (Removed ambiguous glyphs: B, C, G, I, J, K, O, P, Q, S, U, V, W, X, Y, Z)
  • Lowercase Alphabet (6 chars): defhmt (Removed lookalike and mirror glyphs: a, b, c, g, i, j, k, l, n, o, p, q, r, s, u, v, w, x, y, z)
  • Numeric Digits (7 chars): 2346789 (Removed 0, 1, 5 to eliminate confusion with O, I, l, S)
  • Special Symbols (9 chars): @#$%&*+=? (Removed quotes, brackets, hyphens, underscores)
|\mathcal{C}| = 10 + 6 + 7 + 9 = 32 = 2^5\text{ characters}

Mathematical Proof of Zero Modulo Bias:

Let $B \in \{0, 1, \dots, 255\}$ be a uniformly distributed pseudorandom byte generated by HMAC-SHA512. The maximum aligned boundary $\text{validMax}$ is calculated as:

\text{validMax} = 256 - (256 \pmod{32}) = 256 - 0 = 256

Because $256$ is an exact integer multiple of $32$ ($2^8 / 2^5 = 2^3 = 8$ exact full cycles):

\forall c \in \mathcal{C}, \quad \Pr[\text{byteToChar}(B) = c] = \frac{8}{256} = \frac{1}{32} = 0.03125000\dots

Every character in the pool receives exactly equal probability of selection. Modulo bias loss is mathematically 0.000% (Zero Loss). No derived pseudorandom entropy is wasted or discarded.

7. Usable Security & The Science of Input Normalization

In deterministic key derivation systems, human typing variability is the primary operational failure point. When entering a master secret on mobile devices, modern virtual keyboards introduce automatic transformations:

  • Automatic capitalization of the first letter (e.g. MySecret vs mysecret).
  • Automatic insertion of smart punctuation or directional quotes.
  • Trailing whitespace added during auto-complete suggestions.

In un-normalized systems, a single accidental space alters the entire derived password, causing authentication failures. FrankPass incorporates MMY Aggressive Input Normalization ($\mathcal{N}_{\text{aggressive}}$) and Unicode NFC Composition ($\mathcal{P}_{\text{NFC}}$) before derivation:

// Exact Canonical Normalization Implementation:
const normalizedSecret = (secretKey || '')
    .toLowerCase()
    .replace(/\s+/g, '')
    .replace(/[^a-z0-9]/g, '');

This guarantees that variations such as "Master Secret 2026! ", "mastersecret2026", and "master secret 2026" always map to the exact same canonical byte array, eliminating cross-device human error while preserving high entropy.

8. Threat Model & Security Properties

1. Server Compromise & Zero-Storage Immunity:

Because FrankPass servers store zero credentials, zero master keys, and zero ciphertext blobs ($0\text{ bytes stored}$), a total compromise of the hosting infrastructure, edge CDNs, or DNS routers yields zero actionable data to an adversary.

2. Cryptographic Domain Separation:

By injecting the domain name into length-prefixed netstrings and salting the HMAC-SHA512 PRF, outputs across different platforms ($D_1 \neq D_2$) are computationally indistinguishable from independent random variables. A data breach at Service A gives an attacker zero mathematical leverage to predict credentials for Service B.

3. Air-Gapped & 100% Offline Survivability:

FrankPass contains zero runtime network dependencies. Once cached by the Service Worker or saved as a standalone single-file HTML document ($150\text{ KB}$), the engine executes client-side on completely air-gapped computers without internet connectivity.
